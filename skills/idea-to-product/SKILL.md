# 成器｜idea-to-product

把用户的想法转化为可运行、可展示、可验证的作品。先读取已有材料，找当前最需要完成的阶段；已有授权和决策不重复询问。只做用户请求的范围，不强制完整流程。

## 路由

三个阶段技能位于此目录的相邻文件夹；读取匹配阶段，不一次加载全部。

| 当前任务 | 读取 | 完成依据 |
|---|---|---|
| 用户、需求、定位、对标、范围不清 | [idea-to-product-plan](../idea-to-product-plan/SKILL.md) | 具体用户任务、范围、交付物、验收与验证计划 |
| 流程、信息结构、视觉或内容表达需要设计 | [idea-to-product-design](../idea-to-product-design/SKILL.md) | 可评审的体验与状态、视觉依据、开发交接 |
| 需要实现、集成、修复或运行验证 | [idea-to-product-develop](../idea-to-product-develop/SKILL.md) | 可运行结果与验收证据 |
| 需要演示、内容预测、发布登记或复盘 | [内容校准](references/calibration.md) | 事前记录与实绩分离、来源可追溯 |

相邻技能缺失时，按上表交付标准继续，说明当前使用简化流程；不要假装已调用未安装的技能。若已安装 DBS 或 cheat-on-content，按需读取具体技能；它们不是强制依赖。读取文档不等于获得发布或其他外部操作授权。

## 发布前模拟与版本选择

用户说“模拟受众”“预测哪版更好”“A/B 测试文案”“发布前测试”“CrowdTest 模式”，读取 [发布前模拟](references/preflight.md)。生成或接收多个文案版本，按相同受众与指标模拟反应，比较版本并交付推荐稿及依据，再接内容校准。没有历史校准时只做相对选择，不虚构互动量或爆款概率。

## 预测、复盘与状态入口

- “预测”：先从对象判断路由，文案/标题/封面/推文用发布前模拟与内容校准，产品假设用实验闭环；对象不明时问一个具体问题。
- “登记实验”：读取 [实验闭环](references/experiments.md)，对指定的策划、设计或开发假设写事前记录。
- “复盘”“数据来了”：内容记录读取内容校准，产品实验读取实验闭环；检查原预测和数据口径，写复盘并更新对应阶段决策。
- “状态”“待验证”：列出实验 ID、阶段、观察窗口、状态、缺失证据和下一动作，不自动创建提醒。
- 内容预测使用 [内容校准](references/calibration.md)；使用完整 cheat 时复用其日志，不双记。

## 阶段衔接

1. 从对话和项目提取目标、约束、现有产物、事实与未验证假设。确认当前项目目录，检查仓库说明。
2. 明确本次完成态：交付什么、怎样检查、哪些部分依赖用户或外部服务。只问影响实施的缺失信息；其他选择标为假设后推进。
3. 验证关键假设前按 [实验闭环](references/experiments.md) 固定输入版本、预期和否证条件。已见本次结果只能记回顾；历史事实可作新实验基线。然后执行所需阶段。上一阶段已有足够证据就复用，缺口只补到能继续的程度。全流程请求在授权范围内接着完成设计和开发，不停在计划。
4. 每次交接记录：输入文件、决定、产物、验收结果、未验证项、下一阶段动作。设计和开发都能推翻策划假设，回到对应决定修改，记录影响。
5. 实测后复盘事前判断，记录继续、调整、停止或证据不足，将决定交回具体板块。没有数据时报告“产物完成，验证待办”，不称商业或体验假设已通过。交付后需要推广时，把实际能力变成演示与内容；内容与产品采用不同验证指标。

## 项目记录

持续项目按需创建 `.idea-to-product/brief.md`、`design.md`、`delivery.md`、`status.json`；参考 [记录契约](references/project-records.md)。一次小修改可以直接在回复中记录，不强建目录。源码继续放原项目结构，不搬进记录目录。已有文件只更新相关字段，避免覆盖用户内容。运行数据、用户信息和秘密默认不进入公开仓库。

## 完成判断

报告实际完成的结果、可打开产物、如何运行或使用、已做验证及限制。区分设计稿、交互原型、已接真实服务的应用与已上线产品。真实执行证据缺失时明确写未验证。

全流程不默认包含付费服务调用、社交发布、部署或创建公开 GitHub 仓库；用户已明确授权对应操作时继续执行。状态不确定的外部写操作先查结果，再决定重试。没有授权时先完成可评审发布包，说明剩余动作。
